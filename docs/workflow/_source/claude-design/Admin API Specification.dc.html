CMS/MAM Workflow Admin API Specification

워크플로우 관리자 API 상세 명세서 — Laravel + PostgreSQL, 관리자 권한 기반

문서 버전 1.0 · 작성일 2026-07-04 · 상태: DRAFT · 선행 문서: DB Table Spec · Queue & Worker Spec · State Machine Spec · Admin UI Wireframe Spec (각 v1.0)

1. 문서 목적

본 문서는 관리자 화면 9개가 사용하는 API의 요청 파라미터·응답 스키마·권한·상태 전이 조건·에러 코드·감사 로그 기준을 정의한다. 이 API군은 단순 조회가 아니라 운영 행위(재시도·취소·Lock 회수·Worker 관리·재처리)를 안전하게 수행하기 위한 관리자 전용 API다. 모든 조작 API는 ① StateMachine 서비스 경유 상태 변경 ② 감사 로그 기록을 전제로 하며, 이를 우회하는 구현은 금지한다.

9. 콘텐츠 재처리 API

POST /admin/workflows/contents/{id}/reprocess

// 요청
{ "mode": "failed_from",            // failed_from | full
  "reason": "TC 프로파일 변경 재처리", // 필수
  "priority": 200,                   // 선택, 기본 200(수동 재처리)
  "keep_existing_renditions": true,  // full 모드에서만 의미
  "requested_job_type": null }       // 특정 job만 재실행 시 (예: "CA")

// 응답 201
{ "success": true, "data": {
  "new_instance_id": 7002, "content_status": "PROCESSING",
  "created_jobs": [ { "job_id": 90101, "job_type": "TC", "status": "READY" }, … ] } }
정책내용
가능 상태contents = READY 또는 FAILED. DELETED는 CONTENT_DELETED(409), PROCESSING은 INVALID_STATE_TRANSITION(409 — 기존 취소 후 재처리 안내)
인스턴스기존 인스턴스는 되살리지 않음 — 항상 새 workflow_instance 생성. failed_from은 성공 job의 결과를 재사용하고 실패 지점 이후만 job 생성
이력기존 logs/histories 전부 보존
감사reason 필수, 감사 로그 기록

10. 콘텐츠 취소 API

POST /admin/workflows/contents/{id}/cancel — body: { "reason": "잘못된 파일 업로드" } (필수)

  • contents = PROCESSING에서만 가능 — 아니면 CONTENT_NOT_PROCESSING(409).
  • 단일 트랜잭션: WAITING/READY/RETRY job → CANCELED, RUNNING job → cancel_requested_at 마킹(Worker 미응답 30초 시 Scheduler 강제 CANCELED), instance → CANCELED, contents → FAILED가 아닌 REGISTERED로 회귀시키지 않고 FAILED 처리 여부는 정책 플래그 — 기본은 contents=FAILED(note=canceled).
  • 응답: 취소된 job 수, cancel_requested job 수.

13. Job 재시도 API

POST /admin/workflows/jobs/{id}/retry

// 요청
{ "reason": "스토리지 복구 후 재시도",  // 단건 선택 / 일괄 필수
  "reset_retry_count": true,           // 기본 true
  "priority": 200 }                    // 선택

// 응답
{ "success": true, "data": {
  "job_id": 90003, "status": "RETRY", "retry_count": 0,
  "next_attempt_at": "2026-07-04T11:32:00Z" } }
  • FAILED에서만 가능 — SUCCESS/SKIPPED/CANCELED는 INVALID_STATE_TRANSITION(409), RUNNING은 JOB_ALREADY_RUNNING(409).
  • 일괄 재시도: POST /jobs/retry-batch body { "job_ids": […], "reason": "…" } — reason 필수, 응답에 건별 성공/실패 목록.
  • StateMachine 경유(FAILED→RETRY, actor=admin) · 기존 logs/histories 보존 · 감사 로그 기록.

14. Job 취소 API

POST /admin/workflows/jobs/{id}/cancel — body: { "reason": "…" } (필수)

  • WAITING/READY: 즉시 CANCELED + 후속 job SKIPPED(전파) — 응답에 skipped_job_ids 포함.
  • RUNNING: cancel_requested_at 마킹 → 202 Accepted 반환("state": "cancel_requested") → Worker 중단 시 CANCELED. 30초 미응답 시 Scheduler 강제 CANCELED + lock 회수.
  • 종결 상태는 INVALID_STATE_TRANSITION(409).

15. Lock 강제 회수 API

POST /admin/workflows/jobs/{id}/release-lock — 권한 workflow.release_lock (HIGH)

// 요청
{ "reason": "worker 응답 없음, 인프라 확인 완료",  // 필수
  "target_status": "RETRY" }                      // RETRY(기본) | FAILED

// 응답
{ "success": true, "data": { "job_id": 90007, "status": "RETRY",
  "released_lock": { "was_locked_by": 3, "locked_since": "…" } } }
에러 케이스코드 / 처리
lock 없음JOB_LOCK_NOT_FOUND(409) — 이미 회수·완료됨. current_state 반환
job이 RUNNING 아님JOB_NOT_RUNNING(409)
Worker가 직전에 완료CAS 충돌 → INVALID_STATE_TRANSITION(409) + current_state=SUCCESS — UI는 재조회 안내
동시 회수 경합트랜잭션 내 lock 행 FOR UPDATE — 후행 요청은 JOB_LOCK_NOT_FOUND

회수 후 늦게 도착하는 Worker 결과는 lease fencing(worker_id CAS)으로 자동 폐기된다. UI 모달에는 이 사실과 함께 job_id 타이핑 확인을 요구한다.

16. Job 우선순위 변경 API

PATCH /admin/workflows/jobs/{id}/priority — body: { "priority": 300, "reason": null }

  • 가능 상태: WAITING/READY/RETRY. RUNNING/종결 상태는 INVALID_STATE_TRANSITION(409).
  • priority 범위: 0~1000 (기본 100 / 재색인 50 / 수동 200 / 긴급 300). 범위 외 422.
  • reason은 선택 — 상태를 바꾸지 않는 LOW 위험 조작이므로 강제하지 않되 감사 로그에는 항상 기록.

18. Worker 비활성화 API

POST /admin/workflows/workers/{id}/disable — body: { "reason": "OS 패치", "drain": true }

  • ONLINE/BUSY에서 가능. reason 필수.
  • drain=true(기본): DISABLED 마킹 → 신규 Claim 중단, 진행 중 job은 완료까지 대기. 응답에 draining job 목록.
  • drain=false: 진행 중 job에 cancel 신호 + 미응답 시 lock 회수(RETRY 재배정) — 위험도 HIGH 경고를 응답 meta에 포함, UI는 이중 확인.

19. Worker 재활성화 API

POST /admin/workflows/workers/{id}/enable — body: { "reason": null } (선택)

  • DISABLED에서만 가능 — 아니면 WORKER_NOT_DISABLED(409).
  • heartbeat 수신 중이어야 ONLINE 전환 — 90초 이상 미수신이면 WORKER_HEARTBEAT_MISSING(409, "프로세스 기동 확인 필요").
  • reason 선택(활성화는 LOW 위험) — 감사 로그는 기록.

20. Worker ERROR 해제 API

POST /admin/workflows/workers/{id}/clear-error — body: { "reason": "ffmpeg 크래시 원인 제거 확인" } (필수)

  • ERROR에서만 가능. ERROR→ONLINE, 자동 복귀 없음 — 운영자 확인이 전제.
  • reason 필수 + 감사 로그. 해제 직후 연속 실패 임계가 재발하면 다시 ERROR 전환(Worker 자체 판단).

21. 알림 목록 / 확인 API

GET /admin/workflows/alerts — 필터: severity · acknowledged · event_type · date_from/to.

  "alert_id": 501, "severity": "HIGH", "event_type": "REQUIRED_JOB_FAILED",

23. 상태 기계 연동 정책

  • 모든 조작 API는 JobStateMachine/ContentStateMachine/WorkerStateMachine을 경유 — Controller에서 직접 Eloquent update 금지.
  • 전이 실패(CAS 0행 또는 전이표 거부) 시 409 + current_state + allowed_actions(현재 상태·권한 기준 가능한 액션 배열) 반환 — UI는 이 값으로 화면을 즉시 갱신한다.
  • 동시 조작 경합(두 관리자가 동시 재시도 등): 먼저 성공한 쪽만 반영, 나머지는 409 — 멱등 성격의 조작(이미 목표 상태)은 200으로 흡수.

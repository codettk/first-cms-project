CMS/MAM Workflow Incident Response Runbook

워크플로우 장애 대응 Runbook — 운영자 실무 절차서

문서 버전 1.0 · 작성일 2026-07-04 · 상태: DRAFT · 선행 문서: 설계 문서 12종 (각 v1.0)

1. 문서 목적

장애 상황에서 운영자가 어떤 화면을 보고 → 어떤 로그·쿼리로 원인을 좁히고 → 어떤 관리자 액션을 어떤 기준으로 수행할지를 정의한다. 재시도·취소·Lock 회수·Worker 비활성화·재처리의 판단 기준과, Master 원본 보호 원칙, 감사 로그 기록 기준을 포함한다.

2. 장애 대응 기본 원칙

  • Master Storage의 원본은 어떤 상황에서도 삭제·수정하지 않는다.
  • 원인 확인 전 대량 재시도 금지 — 같은 원인이면 실패만 반복되고 로그가 오염된다.
  • 필수 실패(콘텐츠 차단)와 선택 실패(경고)를 먼저 구분한다.
  • 분류 우선: Worker 장애인가 / Storage 장애인가 / 사용자 파일 문제인가 / 외부 시스템(검색엔진)인가.
  • HIGH 위험 조작(Lock 회수·Worker 관리)은 사유 입력 + 감사 로그 필수.
  • Lock 강제 회수는 heartbeat·Worker 상태 확인 후에만 (§14).
  • 재처리는 항상 새 workflow_instance 생성 — 기존 인스턴스를 되살리지 않는다.
  • 동일 장애 반복 = 개별 Job 문제가 아닌 시스템 문제 — 개별 조치를 멈추고 상위 원인 조사.

7. Worker OFFLINE 대응 (상세)

  1. Worker 상태 화면 — last_heartbeat_at·delay 확인 (90초+ = OFFLINE 판정).
  2. current_job_id·보유 lock 확인 (§18 SQL-4) — 실행 중이던 job 파악.
  3. 서버 접속: supervisor 상태(supervisorctl status) · Worker 프로세스 로그 · 리소스(CPU/메모리/디스크).
  4. 프로세스 죽음 확인 시 재시작 → ONLINE 회복 + heartbeat 재개 확인.
  5. lock 회수: Scheduler가 lease 만료 시 자동 회수(RETRY) — 기본은 대기. 긴급하면 Worker 사망 확인 후 수동 회수(§14).
  6. RUNNING job → RETRY 전환은 자동 회수에 맡기고, 수동 개입은 SEV1·2 상황에서만.
  7. 동일 Worker 반복 OFFLINE(24h 내 3회+) → DISABLED 처리 후 인프라 점검 이관.

8. Worker ERROR 대응 (상세)

  1. ERROR 전환 원인 확인 — Worker 로그에서 연속 실패 job_type·예외 확인.
  2. 외부 도구 점검: 부팅 점검 명령 수동 실행(ffmpeg -version 등) · Storage 접근 테스트 · Worker 버전 확인(배포 직후면 롤백 검토).
  3. 해제 전 기준: 원인이 식별되고 제거되었을 때만 clear-error — 원인 불명 상태 해제 금지(재발 시 실패 job만 늘어남).
  4. clear-error 액션(사유 필수) → ONLINE 복귀 → 첫 job 1~2건 성공 감시.
  5. 해제 후 동일 원인 재발 → DISABLED 처리 + 개발팀 이관.

9. TC / ffmpeg 장애 대응

  1. Job 로그에서 command·stderr 마지막 20줄 확인 — 오류 메시지로 분류.
  2. 입력 codec 확인(media_info) — 미지원 codec이면 PERMANENT 처리 + 프로파일/지원 목록 개정 검토.
  3. transcode_profile 활성·파라미터 확인 (프로파일 변경 직후면 유력 원인).
  4. GPU 인코더 오류(NVENC) → GPU 상태(nvidia-smi) 확인 → GPU Worker DISABLED 후 CPU 풀로 우회(fallback), GPU 복구 후 재활성.
  5. 디스크 여유·임시 경로(.tmp/{job_id}) 확인 — DISK_FULL이면 §10.
  6. 재시도 판단: 도구 크래시·타임아웃=재시도 가능 / 입력 파일 문제=PERMANENT.

10. Storage 장애 대응

  1. zone별 접근 확인: TEMP/MASTER/PROXY/THUMBNAIL/CATALOG/DOCUMENT — mount(df -h, mount)·권한·용량.
  2. I/O 오류 로그(시스템 로그 + job logs STORAGE_IO) 대조 — 특정 zone 집중인지 전역인지.
  3. 용량 부족: CLEANUP 배치 즉시 실행 + temp 유예 기간 단축 검토. Master는 정리 대상 아님.
  4. checksum 불일치: 해당 콘텐츠 격리(재시도 중단) → 원본·사본 대조 → 무결성 사고로 개발팀 이관 (SEV2+).
  5. 장애 중: 해당 zone에 쓰는 Worker 유형 DISABLED(drain) — 실패 누적 방지.
  6. 복구 후: 테스트 파일 write/delete 확인 → Worker enable → STORAGE_ERROR 실패 job 일괄 재시도.

11. Search Index 장애 대응

  1. search_index_states FAILED/STALE 건수(§18 SQL-9) + INDEX job 실패 로그 확인.
  2. 검색엔진 cluster health 확인 — red/yellow면 인프라 대응 우선 (SEV2).
  3. mapping conflict(특정 콘텐츠만 실패) → 해당 필드 데이터 확인 후 개발팀 이관 — 재시도 무의미.
  4. INDEX는 필수 job — 장애 지속 시 신규 콘텐츠 PUBLISH가 전부 차단됨을 인지. 강제 PUBLISH 금지 — 검색 불가 콘텐츠 양산.
  5. 복구 후: FAILED INDEX job 일괄 재시도(사유 기록) → search_index_states INDEXED 회복 확인 → STALE 잔량은 자동 재색인 확인.

12. PUBLISH 실패 대응

  1. 실패 사유 확인 — 필수 job 미완료인지 rendition 누락인지(history note에 MISSING_RENDITION:*).
  2. 필수 job 전체 SUCCESS 확인(§18 SQL-6) → 미완료면 해당 job부터 처리.
  3. rendition 누락: DB 행 존재 + 파일 실재(stat) 대조 → 파일만 없으면 Storage 사고(§10), 행도 없으면 생성 job 미실행.
  4. MASTER 누락은 §6-11 (SEV1 취급).
  5. 생성 job(TC/CA/DOC_PREVIEW) 재실행 → 성공 확인 → PUBLISH 재시도.
  6. 강제 PUBLISH 금지 — 필수 산출물 없는 READY는 웹 표출 깨짐으로 직결.

14. Lock 강제 회수 기준

  • 회수 가능: ① heartbeat 90초+ 중단 ② locked_until 경과 ③ Worker 프로세스 사망 확인 ④ RUNNING이 timeout 초과 ⑤ Worker가 DISABLED/ERROR 전환됨 — 이 중 하나 이상 + 로그로 교차 확인.
  • 회수 금지: 단순히 오래 걸린다는 이유(진행률이 갱신 중이면 정상 실행) — timeout과 자동 회수에 맡긴다.
  • 절차: Job 로그·진행률 갱신 시각 확인 → Worker 상태 확인 → release-lock(사유 필수, HIGH) → RETRY 전환 확인.
  • 회수 후 원래 Worker가 늦게 보내는 결과는 fencing이 자동 폐기(WARN 로그) — 별도 조치 불필요.

16. Worker 비활성화 기준

  • 대상: 동일 Worker 동일 job_type 실패 반복 · 외부 도구 오류 반복 · Storage 접근 이상 · 배포/점검 예정 · 해당 Worker만 heartbeat 불안정 · GPU 장애.
  • drain=true(기본): 진행 중 job 완료 후 유휴 — 배포·점검·성능 저하 등 비긴급 상황.
  • drain=false: 진행 중 job도 중단(RETRY 재배정) — 잘못된 산출물을 만들고 있거나 Storage를 오염시키는 긴급 상황만. 이중 확인 필수.

17. 관리자 조작별 주의사항

조작위험도사유수행 전 확인 → 수행 후 확인
Job 재시도LOW선택원인 제거 여부 → RETRY→READY→SUCCESS 진행
일괄 재시도MED필수동일 fail_reason끼리만·원인 제거 → 부분 실패 목록 확인
Job 취소MED필수후속 SKIPPED 전파 영향 → 콘텐츠 상태 확인
Lock 강제 회수HIGH필수§14 기준 충족 → RETRY 전환 + 재실행 성공
콘텐츠 재처리MED필수모드(failed_from/full) 적절성 → 새 인스턴스 진행
콘텐츠 취소MED필수사용자 영향(FAILED 처리됨) → job 일괄 CANCELED 확인
Worker 비활성화MED필수drain 모드·잔여 용량 → 큐 적체 감시
ERROR 해제HIGH필수원인 제거 확인(§8) → 첫 job 성공 감시
PUBLISH 재시도LOW선택필수 산출물 존재(§12) → READY 전환

18. 장애 대응 SQL 예시

-- 1) 상태별 Job 수 (type별)
SELECT job_type, status, count(*) FROM workflow_jobs
WHERE created_at > now() - interval '24 hours' GROUP BY 1, 2 ORDER BY 1, 2;

-- 2) Worker heartbeat delay
SELECT worker_name, status, EXTRACT(EPOCH FROM now() - last_heartbeat_at)::int AS delay_sec,
       current_job_id FROM workflow_worker_agents ORDER BY delay_sec DESC NULLS LAST;

-- 3) RUNNING 중 timeout 임박 (80%+)
SELECT id, job_type, worker_id, started_at,
       EXTRACT(EPOCH FROM now() - started_at)::int AS elapsed, timeout_sec
FROM workflow_jobs WHERE status = 'RUNNING'
  AND now() - started_at > make_interval(secs => timeout_sec * 0.8);

-- 4) expired lock 목록
SELECT l.job_id, l.locked_by_worker_id, l.locked_until, j.job_type, j.status
FROM workflow_job_locks l JOIN workflow_jobs j ON j.id = l.job_id
WHERE l.locked_until < now();

-- 5) 최근 실패 Job (사유 집중도)
SELECT fail_reason_code, job_type, count(*) FROM workflow_jobs
WHERE status = 'FAILED' AND finished_at > now() - interval '6 hours'
GROUP BY 1, 2 ORDER BY count(*) DESC;

-- 6) 특정 콘텐츠의 job 상태
SELECT job_type, status, retry_count, fail_reason_code, started_at, finished_at
FROM workflow_jobs WHERE content_id = :cid
  AND instance_id = (SELECT max(id) FROM workflow_instances WHERE content_id = :cid)
ORDER BY id;

-- 7) 특정 Worker의 최근 실패
SELECT id, job_type, fail_reason_code, finished_at FROM workflow_jobs
WHERE worker_id = :wid AND status = 'FAILED' ORDER BY finished_at DESC LIMIT 20;

-- 8) 필수 rendition 누락 (READY 전 콘텐츠 검증 — 영상 예)
SELECT c.id FROM contents c
WHERE c.media_type = 'VIDEO' AND c.status = 'PROCESSING'
  AND NOT EXISTS (SELECT 1 FROM media_renditions r
    WHERE r.content_id = c.id AND r.rendition_type = 'PROXY_VIDEO');

-- 9) 색인 이상 목록
SELECT content_id, status, last_error, indexed_at FROM search_index_states
WHERE status IN ('FAILED','STALE') ORDER BY indexed_at NULLS FIRST LIMIT 50;

-- 10) 최근 관리자 조작
SELECT actor_user_id, action, target_type, target_id, reason, created_at
FROM admin_audit_logs ORDER BY created_at DESC LIMIT 30;

20. 복구 후 검증 체크리스트

  • ☐ Worker 전원 ONLINE/BUSY (OFFLINE·ERROR 0)
  • ☐ READY Queue 감소 추세 · RUNNING 정상 진행(진행률 갱신)
  • ☐ FAILED·TIMEOUT 증가 정지 · Lock 회수 반복 중단
  • ☐ 신규 콘텐츠 1건 업로드 → READY 전환 end-to-end 확인
  • ☐ Search Index INDEXED 회복 · STALE 잔량 소진 중
  • ☐ 수행한 모든 수동 조작이 audit_logs에 사유와 함께 기록됨
  • ☐ 장애 영향 콘텐츠 목록 확보 → 재시도/재처리 완료 → READY 확인

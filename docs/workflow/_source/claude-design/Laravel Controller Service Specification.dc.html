1. 문서 목적

Admin API Spec v1.0의 17개 엔드포인트를 Laravel Controller / FormRequest / Service / Resource 구조로 구현하기 위한 기준을 정의한다. 핵심 원칙: ① 상태 전이는 StateMachine 서비스로 일원화(직접 update 금지) ② 조회(Query)와 조작(Command) Service 분리 ③ 감사 로그는 조작 트랜잭션과 동일 트랜잭션 ④ available_actions 계산은 서버 단일 위치 ⑤ 예외 → 표준 에러 응답 자동 매핑.

TransactionService는 별도로 두지 않는다 — CommandService가 최상위 DB::transaction()을 소유하고, StateMachine은 그 안에서 CAS+history만 수행한다(내부 트랜잭션 금지). 단독 전이는 TransitionRunner wrapper가 트랜잭션을 소유한다.

7. StateMachine Service 구현

abstract class AbstractStateMachine {
  /** @var array<string, string[]> */ protected const TRANSITIONS = [];

  public function canTransition(string $from, string $to): bool {
    return in_array($to, static::TRANSITIONS[$from] ?? [], true);
  }
  public function assertTransition(string $from, string $to): void {
    if (! $this->canTransition($from, $to))
      throw new InvalidStateTransitionException($from, $to);
  }
  // 자체 트랜잭션을 열지 않는다 — 호출부(CommandService)의 트랜잭션 안에서 실행
  public function transition(Model $model, string $to, string $actor, ?string $note = null): TransitionResult {
    $from = $model->status->value;
    $this->assertTransition($from, $to);
    assert(DB::transactionLevel() > 0);                          // 호출부 트랜잭션 필수
    $updated = DB::update(                                       // CAS
      "UPDATE {$model->getTable()} SET status = ?, updated_at = now()
       WHERE id = ? AND status = ?", [$to, $model->id, $from]);
    if ($updated === 0)                                          // 동시성 충돌
      return TransitionResult::conflict($model->fresh()->status->value);
    $this->writeHistory($model->id, $from, $to, $actor, $note);  // jobs만 — 같은 트랜잭션
    return TransitionResult::ok($from, $to);
  }
  abstract public function allowedActions(Model $model, User $user): array;
}
// JobStateMachine: TRANSITIONS = State Machine Spec §5 전이표
// ContentStateMachine · WorkflowInstanceStateMachine · WorkerStateMachine · SearchIndexStateMachine 동일 패턴

TransitionResult::conflict는 예외가 아닌 값 — 호출부(CommandService)가 이미 목표 상태면 멱등 성공, 아니면 409로 변환한다. Worker 완료 기록처럼 fencing이 필요한 경로는 CAS WHERE에 worker_id 추가 오버로드 사용.

public function forJob(WorkflowJob $job, User $u): array {
  $a = [];
  if ($u->can('workflow.logs.view')) $a[] = 'view_logs';
  if ($u->can('workflow.view')) $a[] = 'view_content';
  if ($job->status === JobStatus::Failed && $u->can('workflow.retry')) $a[] = 'retry';
  if (in_array($job->status, [JobStatus::Waiting, JobStatus::Ready, JobStatus::Running])
      && $u->can('workflow.cancel')) $a[] = 'cancel';
  if ($job->status === JobStatus::Running && $job->lock()->exists()
      && $u->can('workflow.release_lock')) $a[] = 'release_lock';
  if (in_array($job->status, [JobStatus::Waiting, JobStatus::Ready, JobStatus::Retry])
      && $u->can('workflow.retry')) $a[] = 'update_priority';
  return $a;
}

9. QueryService 구현 기준

  • dashboard 집계: 상태별 count는 단일 쿼리 GROUP BY status ×3(contents/jobs/workers) + 처리량은 date_trunc('hour', finished_at) 집계. 10초 캐시.
  • contents 목록: 서브쿼리로 current_stage(RUNNING job)·진행률(필수 job 완료 수) 계산 — withCount + addSelect. N+1 방지: with('uploader') + rendition 존재는 EXISTS 서브쿼리.
  • contents 상세: with(['mediaFiles','renditions','instance.jobs.worker','searchIndexState']) eager loading, histories·logs는 최근 N건 제한 쿼리 별도.
  • jobs 목록: timeout_imminent = started_at + timeout_sec×0.8 < now()를 SQL CASE로 계산. progress는 leftJoin(workflow_job_progresses).
  • workers: heartbeat_delay_sec = EXTRACT(EPOCH FROM now() - last_heartbeat_at).
  • sort/filter는 화이트리스트 배열로 검증 — 임의 컬럼 정렬·필터 차단.
  • pagination은 paginate(per_page ≤ 200) — Resource collection + meta 자동.

10. CommandService 구현 기준

공통 흐름: 권한 재확인(Gate) → 트랜잭션 시작 → 대상 lockForUpdate() 재조회 → 상태 검증 → StateMachine.transition(CAS) → 도메인 처리 → AuditLogger.log → 커밋 → available_actions 재계산 후 CommandResult 반환. 충돌 시 InvalidStateTransitionException(409).

조작트랜잭션 내 처리
콘텐츠 재처리content CAS(READY|FAILED→PROCESSING) → 새 instance 생성 → 템플릿 기반 jobs+dependencies 생성(failed_from은 실패 지점 이후만) → audit
콘텐츠 취소비종결 job 일괄 CANCELED(각각 history) → RUNNING job cancel_requested_at 마킹 → instance CANCELED → content FAILED(note=canceled) → audit
Job 재시도FAILED→RETRY CAS → retry_count=0(옵션) → next_attempt_at=now() → priority(옵션) → history+audit

Job 취소WAITING/READY→CANCELED + 후속 SKIPPED 전파 / RUNNING→cancel_requested_at(202) → audit

11. AuditLogger 구현

final class AuditLogger {
  public function log(string $action, Model $target,
      ?string $before, ?string $after, array $payload, ?string $reason): void {
    if (in_array($action, self::REASON_REQUIRED, true) && blank($reason))
      throw ValidationException::withMessages(['reason' => '사유 입력이 필요합니다.']);
    DB::table('admin_audit_logs')->insert([          // 호출부 트랜잭션에 참여
      'actor_user_id' => $this->ctx->userId(),
      'action' => $action,                            // 'job.retry' 라우트명 기반 dot 표기
      'target_type' => $target->getMorphClass(),      // content | job | worker | alert
      'target_id' => $target->getKey(),
      'before_state' => $before, 'after_state' => $after,
      'request_payload' => json_encode($payload),
      'reason' => $reason,
      'ip_address' => $this->ctx->ip(), 'user_agent' => $this->ctx->userAgent(),
      'created_at' => now(),
    ]);
  }
  private const REASON_REQUIRED = ['content.reprocess','content.cancel','job.cancel',
    'job.release_lock','worker.disable','worker.clear_error','content.master_download'];
}

audit 미들웨어가 ip/user_agent/user를 AuditContext에 수집. INSERT 실패 시 예외 전파 → 조작 트랜잭션 전체 롤백(정책 강제).

14. Policy / Gate 설계

  • permission 문자열은 Gate 정의: Gate::define('workflow.retry', fn($u) => $u->hasPermission('workflow.retry')) — 권한 저장은 기존 관리자 권한 테이블 사용.
  • 라우트 ->can()(1차) + FormRequest authorize()(2차) + CommandService 내 재확인(3차, HIGH만).
  • HIGH 권한(release_lock, worker.manage, force_publish, master.download)은 역할 기본 포함 금지 — 개별 부여 + 부여 이력. Gate에서 hasDirectPermission으로만 인정.

17. 코드 예시 — JobRetryService

final class JobRetryService {
  public function __construct(
    private JobStateMachine $sm, private AuditLogger $audit) {}

  public function execute(RetryJobData $d): CommandResult {
    return DB::transaction(function () use ($d) {
      $job = WorkflowJob::lockForUpdate()->findOrFail($d->jobId);

      $result = $this->sm->transition($job, 'RETRY', "admin:{$d->actorUserId}", $d->reason);
      if (! $result->ok) {
        if ($result->conflictCurrentState === 'RETRY')      // 멱등 흡수
          return CommandResult::ok(['status' => 'RETRY']);
        throw new InvalidStateTransitionException('FAILED', 'RETRY',
          current: $result->conflictCurrentState);
      }

      $job->update([                                        // 상태 외 필드 (trigger 통과)
        'retry_count' => $d->resetRetryCount ? 0 : $job->retry_count,
        'next_attempt_at' => now(),
        'priority' => $d->priority ?? $job->priority,
      ]);

      $this->audit->log('job.retry', $job, 'FAILED', 'RETRY',
        ['reset' => $d->resetRetryCount, 'priority' => $d->priority], $d->reason);

      return CommandResult::ok([
        'job_id' => $job->id, 'status' => 'RETRY',
        'retry_count' => $job->retry_count, 'next_attempt_at' => $job->next_attempt_at,
      ]);
    });
  }
}

19. 운영 시 고려사항

  • 직접 DB update·StateMachine 우회 금지 — $fillable에서 status 제외 + 아키텍처 테스트(pest arch)로 강제.
  • 목록 API는 인덱스 활용 확인(EXPLAIN) — 특히 jobs 필터 조합.
  • stdout/stderr 등 대용량은 응답 분리(URL) — Resource에 인라인 금지.
  • Master 다운로드는 본 API군에 포함하지 않는다 — 별도 명세·별도 권한.
  • HIGH 액션은 UI 이중 확인 + 서버 3차 권한 확인이 모두 필요(단일 방어 금지).

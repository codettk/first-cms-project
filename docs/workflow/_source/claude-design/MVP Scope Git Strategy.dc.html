1. MVP 범위

구분항목
포함UPLOAD/REGISTER 연동 · TM · VERIFY · MA · TC(720p 단일) · CA · INDEX · PUBLISH · CLEANUP · Scheduler·Worker 기반 전체 · Audit Log — Admin API/UI 범위는 아래 구분표 참조
제외OCR · STT · AI_ANALYSIS · HLS · 다중 화질(480p/360p) · WAVEFORM · 문서 OCR 고도화 · media_texts 분리 · IMAGE/AUDIO/DOC 파이프라인(M6)
Admin 범위 구분항목
MVP Admin API 포함Dashboard / Contents / Jobs / Workers 조회 API · Job retry API · Job cancel API · release-lock API · Worker disable / enable / clear-error API · Audit Log 기록
MVP Admin UI 포함Dashboard · 콘텐츠 처리 목록 · 콘텐츠 처리 상세 · 실패 Job 확인 · 실패 Job 재시도 · Worker 상태 조회
MVP Admin UI 보류Lock 강제 회수 버튼 · Worker disable / enable / clear-error 조작 버튼 — 조작 API는 MVP에서 구현하되, UI 버튼 노출은 기본 운영 화면에서 보류하고 M6 또는 HIGH 권한 전용 고급 메뉴에서 검토 (운영/복구는 API로 수행 가능)

버튼 노출 원칙: 프론트엔드는 자체 판정 없이 서버가 계산한 available_actions 배열만 기준으로 버튼을 노출한다. MVP 기본 운영 화면에서는 HIGH 위험 조작 버튼이 노출되지 않도록 available_actions 또는 UI 정책으로 통제한다. 단, release-lock / Worker disable / enable / clear-error API 자체는 MVP에서 구현하며, HIGH 권한 전용 화면 또는 직접 API 호출 권한을 가진 운영자에게만 허용한다.

제외 항목은 스키마·전이표에 이미 반영되어 있어(variant_key·선택 작업 정의) 활성화만으로 확장된다 — MVP에서 코드 경로만 미구현.

INDEX 리스크 관리: INDEX는 MVP 필수 job이며 INDEX 성공 후 PUBLISH가 진행되는 설계를 따른다. 검색엔진 연동·폐쇄망 검증 지연 시 일정 리스크 — M3 게이트 전 연결·mapping·upsert·조회 검증 선행 확인. Mock INDEX로 READY를 허용하는 방식은 기본 정책이 아니며, 개발 환경 테스트용으로만 허용한다(운영 MVP 게이트 = 실제 INDEX 성공).

1.1 MVP 완료 기준 (DoD)

  • 영상 파일 업로드 → 사람 개입 없이 contents.status = READY 전환 (성공 시나리오).
  • 웹 상세 화면에서 Proxy 720p 재생 + 썸네일·카탈로그 표출, Master 직접 접근 경로 0건.
  • 운영자가 Admin UI에서 실패 확인 → 사유 열람 → 재시도 → READY 회복 완주.
  • Worker 강제 종료 시 lease 자동 회수 → 다른 Worker가 재실행 (무인 복구).
  • 모든 조작이 admin_audit_logs에 사유와 함께 기록.
  • 조작 API(retry·cancel·release-lock·Worker 관리) 전부 구현 + 계약 테스트 통과 — 단, HIGH 위험 UI 버튼(Lock 회수·Worker 조작)은 기본 운영 화면에 미노출.
  • OpenAPI 계약 테스트·상태 전이 전수 테스트 CI 통과.

1.2 MVP 테스트 시나리오

#시나리오기대 결과
T1정상 영상(MP4/MOV) 업로드8개 job 순차 SUCCESS → READY, rendition 4종+ 생성
T2손상 파일 업로드VERIFY FAILED(PERMANENT) → 후속 SKIPPED → contents FAILED + 알림
T3TC 실행 중 Worker killlease 만료 회수 → RETRY → 재실행 SUCCESS, 늦은 결과 폐기
T4실패 job 수동 재시도FAILED→RETRY→SUCCESS, retry_count 초기화, 감사 로그
T5동시 업로드 10건이중 claim 0건, 전건 READY
T6검색엔진 중단 상태 업로드INDEX RETRY 백오프 → 엔진 복구 후 자동 SUCCESS
T7처리 중 콘텐츠 취소비종결 job CANCELED·RUNNING cancel_requested → 정리 완료

1.3 MVP 이후 확장 (M6 순서 제안)

IMAGE 파이프라인 → AUDIO → DOC(PREVIEW·TEXT_EXTRACT) → OCR·WAVEFORM → 다중 화질·HLS → STT·AI_ANALYSIS → media_texts 검토. 운영 수요에 따라 재조정.

2. Git 전략

2.1 브랜치 전략

브랜치용도 / 규칙
main운영 배포본 — 태그(v0.x) 기반 배포, 직접 push 금지
develop통합 브랜치 — 모든 feature PR의 대상, CI 전체 통과 유지
feature/workflow-engineWBS 2·3 (DB·StateMachine·인스턴스 생성) + 4.3 Scheduler
feature/workflow-workerWBS 4·5·6 (Claim·Worker·Storage·Handler)
feature/workflow-admin-apiWBS 7
feature/workflow-admin-uiWBS 8
hotfix/workflow-*운영 긴급 수정 — main에서 분기, main+develop 동시 머지

feature 브랜치는 장수 금지 — 커밋 단위(§2.2)별로 develop에 자주 머지한다. 하위 작업은 feature/workflow-worker/tc-handler처럼 슬래시 하위 브랜치로.

2.3 PR 기준

  • 1 PR = 1 커밋 단위(위 표) 또는 그 하위 태스크 — 리뷰 가능한 크기(±500라인 목표).
  • 필수 체크: CI 전체 통과 · 관련 설계 문서 § 링크 · 스키마 변경 시 DBA 리뷰 · 상태 전이 관련 변경 시 전이 전수 테스트 첨부.
  • 리뷰 승인 1인 이상(HIGH 위험 영역 — StateMachine·Claim·Storage 가드 — 는 2인).
  • 머지 방식: squash merge (develop) — 커밋 메시지가 §2.4 컨벤션이 되도록.

2.4 테스트 통과 기준 (CI 게이트)

게이트기준

2.5 커밋 메시지 컨벤션

<type>(<scope>): <subject>          # 소문자, 명령형, 마침표 없음

type : feat | fix | test | docs | refactor | chore | perf
scope: workflow | worker | admin | db | ops

예:
feat(workflow): implement job state machine
feat(worker): implement video transcode handler
fix(worker): discard stale results after lease loss
test(workflow): add state transition tests
docs(workflow): update runbook references

2.6 롤백 기준

  • 운영 장애 유발 커밋: revert 커밋으로 되돌림 (force push 금지).
  • DB migration은 롤백하지 않는다 — fix-forward 원칙(Migration Spec §14). 스키마 문제는 새 migration으로 수정.
  • Worker 배포 롤백: DISABLED(drain) → 이전 태그 재배포 → enable.
  • 롤백 시 hotfix 브랜치에서 원인 수정 후 main·develop 동시 반영.

2.7 기능별 작업 순서 (착수 체크리스트)

  1. repo 초기화: main·develop 보호 규칙 + CI 파이프라인 (게이트 5종).
  2. feature/workflow-engine에서 커밋 1~5 순차 진행 — M1 게이트.
  3. feature/workflow-worker에서 커밋 6~7 (엔진 4 이후 병행 가능) — M2 게이트.
  4. 커밋 8~9로 VIDEO 파이프라인 — M3 게이트 (E2E 통과 시 태그 v0.3).
  5. admin-api 커밋 11~12 (커밋 4 이후 병행 가능), admin-ui 커밋 13 — M4 게이트.
  6. 커밋 14 + 부하·장애 리허설 — M5 게이트, 태그 v1.0-mvp.
  7. M6 확장은 커밋 10부터 동일 패턴.

CMS/MAM Workflow Laravel Migration & Seed Specification

워크플로우 Laravel 마이그레이션·시드 설계서 — Laravel 11 + PostgreSQL 15 기준

문서 버전 1.0 · 작성일 2026-07-04 · 상태: DRAFT · 선행 문서: DB Table Spec · Queue & Worker Spec · State Machine Spec · Admin API Spec (각 v1.0)

1. 문서 목적

지금까지 확정한 워크플로우 DB 설계(17개 테이블·CHECK/UNIQUE/FK·partial index·trigger·seed)를 Laravel Migration + Seeder 코드로 곧바로 옮길 수 있는 기준을 제공한다. Schema Builder로 표현 가능한 부분은 Builder를, PostgreSQL 고유 기능(CHECK, partial index, trigger)은 DB::statement()를 사용한다. 본 문서의 코드는 검토용 초안이며, 실제 마이그레이션 파일 작성 시 §3 순서와 §15 롤백 정책을 따른다.

테이블별 컬럼·타입·제약 상세는 DB Table Specification v1.0 §4가 원본 — 본 문서는 구현 코드 관점의 차분(추가 컬럼: jobs.cancel_requested_at·priority, renditions.metadata)만 명시하고 코드 초안에 집중한다.

3. Migration 생성 순서

  1. contents
  2. media_files (FK→contents)
  3. transcode_profiles
  4. media_renditions (FK→contents, media_files, transcode_profiles)
  5. workflow_templates
  6. workflow_template_steps (FK→templates)
  7. workflow_instances (FK→contents, templates)
  8. workflow_worker_agents
  9. workflow_jobs (FK→instances, contents, worker_agents)
  10. workflow_job_dependencies (FK→jobs 자기참조 쌍)
  11. workflow_job_histories / 12. workflow_job_logs (FK→jobs)
  12. workflow_job_locks (FK→jobs, worker_agents) / 14. workflow_job_progresses (FK→jobs)
  13. search_index_states (FK→contents) / 16. admin_audit_logs / 17. workflow_job_allowed_transitions
  14. triggers (모든 테이블 생성 후 별도 migration)

순서 이유: PostgreSQL FK는 참조 대상 테이블이 먼저 존재해야 생성 가능하다. worker_agents는 jobs.worker_id FK 때문에 jobs보다 먼저, trigger는 참조하는 테이블(allowed_transitions 포함)이 모두 만들어진 뒤 마지막에 생성한다. 롤백은 정확히 역순으로 실행된다.

4. 상태값 / CHECK 제약 정의

상태값의 단일 원천은 PHP enum(§14)이고, DB CHECK 제약은 2차 방어선이다. 값 목록은 State Machine Spec §2와 동일. storage_zone은 TEMP · MASTER · PROXY · THUMBNAIL · CATALOG · DOCUMENT · ARCHIVE 7종으로 확정(DOCUMENT·ARCHIVE 추가). CHECK 생성 패턴:

Schema::create('contents', function (Blueprint $t) { … $t->string('status', 20)->default('UPLOADING'); … });

DB::statement("ALTER TABLE contents ADD CONSTRAINT chk_contents_status
  CHECK (status IN ('UPLOADING','REGISTERED','PROCESSING','READY','FAILED','ARCHIVED','DELETED'))");

Laravel 11은 $t->check()가 없으므로 모든 CHECK는 DB::statement()로 추가한다. 제약명은 chk_{table}_{column} 규칙 고정 — 롤백 시 명시적 DROP 가능.

8. workflow_job_progresses 정책

  • job_id PK — job당 1행 upsert(ON CONFLICT (job_id) DO UPDATE).
  • RUNNING job만 갱신(Worker 책임 — FK 외 DB 강제는 두지 않음: 고빈도 UPDATE 경로에 trigger 비용 회피).
  • job 종결 시 Worker가 DELETE, 누락분은 CLEANUP 배치가 종결 job의 행을 일괄 삭제.

9. admin_audit_logs 정책

  • append-only — UPDATE/DELETE 금지 trigger(§12-5) + 애플리케이션 계정 권한 GRANT INSERT, SELECT ONLY.
  • reason 필수 액션: content.reprocess · content.cancel · job.cancel · job.release_lock · worker.disable · worker.clear_error · content.master_download — FormRequest 검증 + AuditLogger에서 2차 assert.
  • 조작 트랜잭션과 동일 트랜잭션에서 INSERT — 기록 실패 시 조작 롤백.

10. Seed 설계

10.1 workflow_job_allowed_transitions

class JobAllowedTransitionSeeder extends Seeder {
  public function run(): void {
    $t = [
      ['WAITING','READY'], ['WAITING','SKIPPED'], ['WAITING','CANCELED'],
      ['READY','RUNNING'], ['READY','SKIPPED'], ['READY','CANCELED'],
      ['RUNNING','SUCCESS'], ['RUNNING','FAILED'], ['RUNNING','RETRY'],
      ['RUNNING','TIMEOUT'], ['RUNNING','CANCELED'],
      ['TIMEOUT','RETRY'], ['TIMEOUT','FAILED'], ['TIMEOUT','CANCELED'],
      ['RETRY','READY'], ['RETRY','FAILED'], ['RETRY','CANCELED'],
      ['FAILED','RETRY'],
    ];
    DB::table('workflow_job_allowed_transitions')->upsert(
      array_map(fn($p) => ['from_status'=>$p[0], 'to_status'=>$p[1]], $t),
      ['from_status','to_status']
    );
  }
}

upsert 사용 — 재실행 멱등. PHP enum 전이맵(JobStateMachine)과 이 seed는 단위 테스트로 일치를 검증한다(§16).

11. PostgreSQL Trigger 초안

-- 1) 상태 전이 검증
CREATE OR REPLACE FUNCTION check_job_transition() RETURNS trigger AS $$
BEGIN
  IF OLD.status = NEW.status THEN RETURN NEW; END IF;
  IF NOT EXISTS (SELECT 1 FROM workflow_job_allowed_transitions
                 WHERE from_status = OLD.status AND to_status = NEW.status) THEN
    RAISE EXCEPTION 'invalid job transition: % -> % (job %)', OLD.status, NEW.status, OLD.id;
  END IF;
  RETURN NEW;
END $$ LANGUAGE plpgsql;
CREATE TRIGGER trg_job_transition BEFORE UPDATE OF status ON workflow_jobs
FOR EACH ROW EXECUTE FUNCTION check_job_transition();

-- 2) updated_at 자동 갱신 (공용)
CREATE OR REPLACE FUNCTION set_updated_at() RETURNS trigger AS $$
BEGIN NEW.updated_at := now(); RETURN NEW; END $$ LANGUAGE plpgsql;
CREATE TRIGGER trg_jobs_updated BEFORE UPDATE ON workflow_jobs
FOR EACH ROW EXECUTE FUNCTION set_updated_at();
-- contents, media_files, worker_agents에도 동일 부착

-- 3) DELETED 콘텐츠 job 생성 금지
CREATE OR REPLACE FUNCTION guard_job_insert() RETURNS trigger AS $$
BEGIN
  IF EXISTS (SELECT 1 FROM contents WHERE id = NEW.content_id AND status = 'DELETED') THEN
    RAISE EXCEPTION 'cannot create job for DELETED content %', NEW.content_id;
  END IF;

END $$ LANGUAGE plpgsql;

14. Rollback 정책

  • 운영 데이터 존재 시 destructive rollback 금지 — 스키마 변경은 롤백이 아닌 전진 migration(fix-forward)으로 처리.
  • down() 순서: trigger DROP → partial index DROP → FK 제약 DROP → 테이블 DROP (§3 역순). trigger가 남은 채 테이블을 지우면 의존 오류.
  • seed rollback: allowed_transitions·templates는 삭제하지 않고 버전 추가/비활성화로 관리 — 실행 중 인스턴스가 참조하기 때문.
  • 테스트/스테이징에서만 migrate:fresh 허용. 운영은 migrate 단방향 + 백업 후 실행.

16. 운영 시 고려사항

  • histories·logs는 데이터 증가 시 월 파티셔닝 전환 — 초기 스키마는 단일 테이블로 시작하되 PK에 created_at 포함 여부를 파티셔닝 전에 결정.
  • jobs·locks는 fillfactor 80 설정(ALTER TABLE … SET (fillfactor=80))을 trigger migration에 포함 검토.
  • gen_random_uuid()는 PostgreSQL 13+ 내장(pgcrypto 불필요) — 13 미만이면 확장 활성 migration 선행.
  • 애플리케이션 DB 계정 권한: histories·audit_logs는 INSERT/SELECT만, DDL은 마이그레이션 전용 계정으로 분리.

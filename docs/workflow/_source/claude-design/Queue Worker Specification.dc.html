CMS/MAM Queue & Worker Architecture Specification

Queue & Worker 설계서 — Laravel + PostgreSQL 기반 DB Polling 워크플로우 실행 구조

문서 버전 1.0 · 작성일 2026-07-04 · 상태: DRAFT · 선행 문서: Job Type Definition v1.0, DB Table Specification v1.0

1. 문서 목적

본 문서는 workflow_jobs에 생성된 작업을 어떤 Worker가, 어떻게 가져가고(Claim), 실행하고, 상태를 변경하고, 실패·재시도·타임아웃을 처리하는지를 정의한다. DB 테이블 명세서 v1.0의 스키마를 실행 관점에서 구체화하며, Scheduler·Worker Agent·Lock의 책임 경계를 확정하여 개발자가 곧바로 구현에 착수할 수 있게 하는 것이 목적이다.

2. 전체 Queue & Worker 아키텍처

CMS Web Server ─(업로드·등록)→ PostgreSQL
      │ Workflow Instance + workflow_jobs 생성 (TM=READY, 나머지 WAITING)
      ▼
Workflow Scheduler (독립 프로세스, 주기 실행)
      │ ① 의존 충족 WAITING → READY   ② RETRY 도래 확인
      │ ③ RUNNING 타임아웃 감시        ④ 만료 Lock 회수  ⑤ Worker 헬스 감시
      ▼
Job Queue = workflow_jobs (status IN READY/RETRY)   ← 별도 MQ 없음, DB가 큐
      ▼ Claim (FOR UPDATE SKIP LOCKED + lease)
Worker Agents ── TM / General / Transcode / Image / Audio / Document / OCR / Index
      │ 실행: Storage 읽기·쓰기, 외부 도구(ffmpeg 등), Search Engine 색인
      ▼
상태 전이(SUCCESS/FAILED/RETRY/TIMEOUT) + histories/logs 기록
      ▼
Scheduler가 후속 Job READY 전환 → … → PUBLISH → contents.status = READY

5. Job Claim 설계

Worker는 아래 단일 트랜잭션으로 Claim한다. 조건: ① status IN (READY, RETRY) ② next_attempt_at ≤ now() ③ 지원 job_type ④ 우선순위·생성순 정렬.

BEGIN;

SELECT id, job_type, payload FROM workflow_jobs
WHERE status IN ('READY','RETRY')
  AND (next_attempt_at IS NULL OR next_attempt_at <= now())
  AND job_type = ANY(:supported_job_types)
ORDER BY priority DESC, created_at ASC
LIMIT 1
FOR UPDATE SKIP LOCKED;
-- 없으면 ROLLBACK 후 폴링 대기 (sleep 2~5s + jitter)

INSERT INTO workflow_job_locks (job_id, locked_by_worker_id, locked_until, heartbeat_at)
VALUES (:job_id, :worker_id, now() + interval '10 minutes', now());

UPDATE workflow_jobs
SET status='RUNNING', worker_id=:worker_id, started_at=now(),
    retry_count = CASE WHEN status='RETRY' THEN retry_count + 1 ELSE retry_count END,
    updated_at=now()
WHERE id=:job_id;

INSERT INTO workflow_job_histories (job_id, from_status, to_status, actor, note)
VALUES (:job_id, 'READY', 'RUNNING', 'worker:' || :worker_id, 'claimed');

COMMIT;
  • SKIP LOCKED으로 다중 Worker 경합 시에도 서로 다른 행을 잡는다 — 대기 없음.
  • workflow_job_locks.job_id가 PK이므로 이중 lease는 INSERT 충돌로 DB가 원천 차단.
  • Claim 실패(충돌·롤백)는 정상 흐름 — 즉시 다음 폴링으로.

6. Job Lock / Lease 설계

항목정책
Lock 생성 시점Claim 트랜잭션 내부 (RUNNING 전환과 원자적)
기본 leaselocked_until = now() + 10분
heartbeat 주기30초 — heartbeat_at = now(), locked_until = now() + 10분으로 연장
장기 실행 JobTC 등은 heartbeat 연장으로 자연 커버. 연장 UPDATE 실패가 2회 연속이면 Worker는 작업을 스스로 중단(결과 폐기)
만료 기준locked_until < now()
만료 시 처리Scheduler가 lock 삭제 → job을 retry_count < max_retry면 RETRY(+백오프), 초과면 FAILED로 전환 + history 기록(actor=system)
Worker 사망 판정last_heartbeat_at이 90초(3주기) 미갱신 → OFFLINE 전환, 해당 Worker의 lock 전부 회수
중복 실행 방지3중 방어: SKIP LOCKED(경합) + locks PK(이중 lease) + CAS UPDATE(WHERE status='RUNNING' AND worker_id=:me)로 결과 기록

회수된 job을 다른 Worker가 이미 재실행 중일 때 죽었던 Worker가 늦게 결과를 쓰는 것을 막기 위해, 모든 완료 UPDATE는 worker_id = :me 조건을 포함한다(lease fencing).

7. Job 상태 전이 (전환 주체)

전이주체조건
WAITING → READYScheduler선행 job 전부 SUCCESS 또는 SKIPPED
READY/RETRY → RUNNINGWorkerClaim 성공 (lock 획득)
RUNNING → SUCCESSWorker성공 조건 충족, result 기록
RUNNING → FAILEDWorker영구 실패 또는 재시도 소진
RUNNING → RETRYWorker / Scheduler일시적 실패(Worker) 또는 lease 만료 회수(Scheduler)
RUNNING → TIMEOUTTimeout Monitor (Scheduler 내)started_at + timeout_sec < now()
TIMEOUT → RETRY / FAILEDScheduler재시도 여력에 따라
RETRY → READYSchedulernext_attempt_at 도래
FAILED → RETRYAdmin관리자 수동 재시도 (retry_count 초기화)
WAITING/READY → SKIPPEDScheduler필수 선행 작업 최종 실패, 또는 조건 미충족(예: OCR 불필요)
WAITING/READY/RUNNING → CANCELEDAdmin / System콘텐츠 삭제·수동 취소

8. Scheduler 설계

Scheduler는 Worker와 분리된 단일 실행 보장 프로세스로 운영한다(다중 기동 대비 advisory lock: pg_try_advisory_lock). 틱마다 순서대로:

  1. READY 전환 — 의존 충족 WAITING job 일괄 UPDATE (§17 SQL-1)
  2. SKIPPED 전파 — 필수 작업 최종 FAILED 시 후속 필수 작업 SKIPPED + 콘텐츠 FAILED
  3. PUBLISH 판정 — 필수 작업 전체 SUCCESS인 인스턴스의 PUBLISH job READY 전환 (선택 작업 실패는 무시)
  4. RETRY 재개 — next_attempt_at 도래한 RETRY → READY
  5. 타임아웃 감시 — 장기 RUNNING → TIMEOUT
  6. Lock 회수 — locked_until < now() lock 삭제 + job RETRY/FAILED
  7. Worker 헬스 — heartbeat 미갱신 Worker OFFLINE 처리

실행 방식 권장: 별도 long-running daemon(Laravel artisan workflow:scheduler 커맨드, supervisor 관리, 내부 10초 루프). Laravel Scheduler(cron, 최소 1분)는 틱 간격이 길어 보조로만 사용. Queue Worker 프로세스와는 반드시 분리한다.

10. 진행률 처리

workflow_jobs에 진행률을 직접 두면 고빈도 UPDATE로 큐 인덱스·row bloat에 악영향 — 별도 테이블 workflow_job_progresses를 공식 테이블로 확정한다 (job_id PK, upsert 전용):

CREATE TABLE workflow_job_progresses (
  job_id                  bigint PRIMARY KEY REFERENCES workflow_jobs(id),
  progress_percent        numeric(5,2) NOT NULL DEFAULT 0,
  progress_message        varchar(500),
  estimated_remaining_sec int,
  updated_at              timestamptz NOT NULL DEFAULT now()
);
  • 갱신 주기: 2~5초 또는 1%p 변화 시. 관리자 화면은 이 테이블만 폴링.
  • TC: ffmpeg -progress pipe:1 출력의 out_time_ms ÷ 원본 duration → %. 남은 시간 = 경과 × (100−p)/p.
  • DOC_PREVIEW: 변환 완료 페이지 수 ÷ 총 페이지 수.
  • OCR: 처리 완료 페이지 수 ÷ 대상 페이지 수.
  • 완료 시 progress 행은 CLEANUP 배치에서 삭제(또는 job 종결 시 DELETE).

11. 실패 및 재시도 정책

실패 분류예시처리
일시적 (TRANSIENT)네트워크 단절, DB 커넥션, 스토리지 일시 오류RETRY + 지수 백오프
영구 (PERMANENT)손상 파일, 비허용 포맷, 암호화 문서즉시 FAILED — 재시도 금지
사용자 파일 문제VERIFY 실패류FAILED + 사용자 안내 문구 매핑
시스템 문제도구 크래시, 메모리 부족RETRY, 반복 시 Worker ERROR 마킹
Worker 문제heartbeat 중단, lease 만료Scheduler 회수 → RETRY
스토리지 문제용량 부족, 마운트 유실RETRY + 운영 알림 (전역 장애 가능성)
  • retry_count는 RETRY → RUNNING 재진입 시점(Claim)에 증가.
  • next_attempt_at = now() + base × 2^(retry_count), base=1분, 상한 30분 (INDEX는 base=30초).
  • retry_count ≥ max_retry면 FAILED 확정. 필수 작업이면 콘텐츠 FAILED + 후속 SKIPPED + 관리자 알림.
  • 선택 작업 FAILED는 콘텐츠 READY를 차단하지 않음 — 대시보드 경고로만 노출.
  • 수동 재시도(Admin): retry_count=0 초기화, FAILED → RETRY, actor=admin:{user_id}로 이력 기록. 실행 이력·로그는 보존.
  • 알림 기준: 필수 작업 최종 FAILED(즉시), 동일 유형 실패율 > 10%/10분(집계), 스토리지·검색엔진 오류(즉시).

12. 우선순위 정책

workflow_jobs의 priority smallint NOT NULL DEFAULT 100 컬럼은 확정 사양이다. Claim 정렬 표준: ORDER BY priority DESC, created_at ASC (전 문서 공통).

상황priority비고
긴급 업로드 (관리자 지정)300인스턴스 생성 시 전체 job에 부여
관리자 수동 재처리200사람이 기다리는 작업 우선
일반 업로드100기본값
메타데이터 수정 재색인50지연 허용
대용량 TC (원본 > 임계값)80짧은 job 고사(starvation) 방지 — 대용량은 전용 Worker로 분리(§13)

짧은 job 우선(SJF)은 채택하지 않는다 — 예측 불확실성 대비 이득이 작고, 대형 job starvation 위험. 대신 Worker 풀 분리로 해결.

13. Worker 확장 전략

  • TRANSCODE: 최우선 확장 대상. READY(TC) 큐 길이 > N 시 노드 추가. GPU 노드는 gpu_available=true로 등록하고 GPU 프로파일 job만 배정. 대용량(payload의 file_size > 임계값) job은 전용 대용량 Worker 풀이 소비 — 일반 풀과 격리.
  • TM: 스토리지 I/O 대역폭이 상한 — 노드 수보다 max_concurrency(2~4)로 제어.
  • OCR: CPU 병목이나 선택 작업 — 저우선순위로 유휴 시간 소화, 필요 시 야간 확장.
  • INDEX: 검색엔진 처리량에 종속 — Worker 증설보다 벌크 색인·배치 크기 조정이 유효.
  • 장애 격리: worker_type별 별도 프로세스/노드. 한 유형의 크래시 루프가 다른 유형을 막지 않는다. DOCUMENT Worker는 LibreOffice를 자식 프로세스로 격리하고 job마다 재기동.
  • 모든 Worker는 무상태(stateless) — 노드 추가/제거만으로 확장, 상태는 전부 DB에.

처리량초당 수천 job에 유리분당 수백 job 수준에 충분 — 미디어 워크플로우 특성상 job 수 적고 실행 시간 김
결론폐쇄망 CMS/MAM에는 PostgreSQL Polling이 적합. job 발생률이 낮고 개별 실행이 길어 폴링 오버헤드가 무시 가능하며, 감사·이력·복구가 SQL로 일원화된다. Laravel Queue는 웹 서버의 경량 비동기(메일·알림)에만 사용.

17. PostgreSQL SQL 예시

SQL-1 · READY 전환 (Scheduler)

UPDATE workflow_jobs j SET status='READY', updated_at=now()
WHERE j.status='WAITING'
  AND NOT EXISTS (
    SELECT 1 FROM workflow_job_dependencies d
    JOIN workflow_jobs p ON p.id = d.depends_on_job_id
    WHERE d.job_id = j.id AND p.status NOT IN ('SUCCESS','SKIPPED'));

SQL-2 · 타임아웃 감시 (Scheduler)

UPDATE workflow_jobs SET status='TIMEOUT', updated_at=now()
WHERE status='RUNNING'
  AND started_at + make_interval(secs => timeout_sec) < now();

SQL-3 · 만료 Lock 회수 (Scheduler)

WITH expired AS (
  DELETE FROM workflow_job_locks WHERE locked_until < now()
  RETURNING job_id
)
UPDATE workflow_jobs j
SET status = CASE WHEN retry_count < max_retry THEN 'RETRY' ELSE 'FAILED' END,
    next_attempt_at = now() + interval '1 minute' * power(2, retry_count),
    updated_at = now()
FROM expired e WHERE j.id = e.job_id AND j.status = 'RUNNING';

SQL-4 · heartbeat 연장 (Worker)

UPDATE workflow_job_locks
SET heartbeat_at=now(), locked_until=now() + interval '10 minutes'
WHERE job_id=:job_id AND locked_by_worker_id=:worker_id;  -- 0 rows = lease 상실 → 작업 중단

SQL-5 · 완료 기록 (Worker, fencing)

UPDATE workflow_jobs
SET status='SUCCESS', result=:result, finished_at=now(), updated_at=now()
WHERE id=:job_id AND status='RUNNING' AND worker_id=:worker_id;  -- 0 rows = 이미 회수됨, 결과 폐기

18. 운영 시 고려사항

  • 폴링 간격 2~5초 + jitter — thundering herd 방지. 유휴 시 간격 점증(back-off polling).
  • Scheduler는 단일 인스턴스 보장(advisory lock). 이중 기동 시 두 번째는 대기.
  • Worker 배포는 drain 방식: 신규 Claim 중단 → 진행 중 job 완료 → 종료. DISABLED 상태 활용.
  • autovacuum 튜닝: workflow_jobs·locks는 UPDATE 빈도가 높음 — fillfactor 80, aggressive vacuum.
  • 모든 시각은 timestamptz(UTC) — Worker 노드 간 시계 오차 대비 NTP 필수.
  • 재해 복구: 재기동 시 Scheduler의 lock 회수 로직만으로 RUNNING 고아 job이 자동 복구되는지 리허설로 검증.

CMS/MAM Workflow State Machine Implementation Specification

워크플로우 상태 기계 구현 명세서 — Laravel + PostgreSQL 상태 전이 검증 기준

문서 버전 1.0 · 작성일 2026-07-04 · 상태: DRAFT · 선행 문서: Job Type Definition v1.0 · DB Table Spec v1.0 · Queue & Worker Spec v1.0

1. 문서 목적

본 문서는 워크플로우에서 발생하는 모든 상태 전이를 단일 기준으로 관리하고, 잘못된 상태 전이·중복 실행·Worker 장애·수동 재시도·PUBLISH 오판정을 방지하기 위한 구현 기준을 정의한다. 5개 상태 관리 대상(contents, workflow_instances, workflow_jobs, workflow_worker_agents, search_index_states)의 상태값·전이표·전환 주체를 확정하고, Laravel StateMachine 서비스와 PostgreSQL 방어선의 역할 분담을 명시한다.

8. PUBLISH 가능 여부 판정

가능 조건(전부 충족): ① 현재 인스턴스의 필수 job 전체 SUCCESS(SKIPPED 제외 — 단 필수 job의 SKIPPED는 실패 전파이므로 불가) ② MASTER rendition 존재 ③ 유형별 웹 표출 rendition 존재(VIDEO: PROXY_VIDEO+THUMBNAIL / IMAGE: PROXY_IMAGE+THUMBNAIL / AUDIO: PROXY_AUDIO / DOC: PAGE_PREVIEW) ④ INDEX job SUCCESS ⑤ contents.status = PROCESSING ⑥ DELETED/ARCHIVED 아님.

불가 조건(하나라도 해당): 필수 job에 FAILED 존재 · 필수 job에 WAITING/READY/RUNNING/RETRY 존재 · 필수 rendition 누락 · INDEX 실패 · 콘텐츠 DELETED.

-- PUBLISH Worker 판정 (단일 트랜잭션)
BEGIN;
SELECT status FROM contents WHERE id=:content_id FOR UPDATE;      -- = 'PROCESSING' 확인

SELECT count(*) FILTER (WHERE status <> 'SUCCESS') AS blocking
FROM workflow_jobs
WHERE instance_id = :instance_id AND is_required
  AND job_type <> 'PUBLISH' AND job_type <> 'CLEANUP';            -- 0이어야 함

SELECT bool_and(cnt > 0) FROM (                                     -- 필수 rendition 존재 검사
  SELECT count(*) cnt FROM media_renditions
  WHERE content_id=:content_id AND rendition_type = ANY(:required_types)
  GROUP BY rendition_type) t;

UPDATE contents SET status='READY', published_at=now()
WHERE id=:content_id AND status='PROCESSING';                       -- CAS
UPDATE workflow_instances SET status='SUCCESS', finished_at=now()
WHERE id=:instance_id AND status='RUNNING';
COMMIT;

rendition 존재는 DB 행 + 스토리지 파일 실재(stat) 이중 확인. 파일 누락 시 PUBLISH는 FAILED 처리하고 해당 생성 job의 수동 재실행을 유도한다(§19-6).

9. 재시도 정책

  • RUNNING → RETRY (Worker: 일시적 실패 / Scheduler: lease 만료 회수), TIMEOUT → RETRY (Scheduler), FAILED → RETRY (Admin 수동), RETRY → READY (Scheduler: next_attempt_at 도래).
  • retry_count 증가 시점: RETRY 상태의 job을 Claim하여 RUNNING으로 전환하는 순간 (Claim 트랜잭션 내). 전환 실패·회수는 카운트하지 않는다.
  • retry_count ≥ max_retry: Scheduler가 RETRY→FAILED 확정 (RETRY 재개 단계에서 검사).
  • next_attempt_at = now() + base × 2^retry_count — base 1분, 상한 30분 (INDEX: base 30초).
  • 수동 재시도: retry_count = 0으로 초기화, FAILED→RETRY, actor=admin:{user_id}. 기존 logs/histories는 전부 보존 — 새 실행은 attempt_no 증가로 구분.
  • rendition 처리: 재실행은 삭제가 아닌 upsert — 동일 (content_id, rendition_type, page_no/timecode_ms) 키의 행과 파일을 덮어쓴다. 파일 교체는 임시 경로에 쓴 뒤 원자적 rename으로 반영(부분 쓰기 노출 방지).

10. TIMEOUT 정책

  • 판단 주체는 Scheduler(Timeout Monitor)다 — Worker 자체 판단에 의존하지 않는다(죽은 Worker는 판단 불가).
  • 조건: status='RUNNING' AND started_at + timeout_sec < now().
  • 처리(단일 트랜잭션): RUNNING→TIMEOUT 전이 + history 기록 → lock DELETE → retry_count < max_retry면 TIMEOUT→RETRY(+백오프), 아니면 TIMEOUT→FAILED. 각 전이마다 history(actor=system, note=timeout).
  • 늦은 결과 폐기(fencing): 죽었다 살아난 Worker의 완료 UPDATE는 WHERE id=? AND status='RUNNING' AND worker_id=:me 조건으로 0행 갱신 → 결과 폐기, 로그에 WARN 기록.

11. CANCELED 정책

  • WAITING/READY 취소: 즉시 CANCELED 전이 + history. lock 없음.
  • RUNNING 취소: ① job에 cancel_requested_at 마킹(또는 별도 신호 테이블) ② Worker가 heartbeat 주기마다 확인 후 실행 중단·부분 산출물 정리 ③ Worker가 RUNNING→CANCELED 전이 + lock 해제. Worker가 30초(1주기) 내 미반응이면 Scheduler가 강제 전이 + lock 회수.
  • 후속 작업: CANCELED job에 의존하는 후속 job은 Scheduler가 SKIPPED 처리(필수 여부 무관 — 인스턴스 진행 불가).
  • 콘텐츠 삭제 시: 해당 콘텐츠의 비종결 job 전체 일괄 CANCELED + 인스턴스 CANCELED (System, 단일 트랜잭션).
  • CANCELED는 종결 — 재개는 새 workflow_instance(또는 새 job) 생성으로만.

15. 상태 전이 이력 기록 정책

  • 모든 상태 전이는 history 기록 필수 — 전이 UPDATE와 history INSERT는 같은 트랜잭션. 하나라도 실패하면 둘 다 롤백.
  • 기록 항목: from_status(생성 시 NULL), to_status, actor(scheduler / worker:{id} / admin:{user_id} / system), note(사유 코드+메시지), created_at.
  • append-only — UPDATE/DELETE 금지 (테이블 권한에서 애플리케이션 계정에 INSERT/SELECT만 부여).
  • 관리자 화면 타임라인: job 상세에서 created_at 순 세로 타임라인으로 표시 — 상태 뱃지, actor, note, 구간 소요 시간(다음 전이와의 차).

16. Laravel 구현 기준

// 상태 전이표는 PHP enum + 상수 맵으로 관리 (config 파일보다 타입 안전)
enum JobStatus: string {
  case Waiting='WAITING'; case Ready='READY'; case Running='RUNNING';
  case Success='SUCCESS'; case Failed='FAILED'; case Retry='RETRY';
  case Skipped='SKIPPED'; case Canceled='CANCELED'; case Timeout='TIMEOUT';
}

class JobStateMachine {
  private const TRANSITIONS = [
    'WAITING' => ['READY','SKIPPED','CANCELED'],
    'READY'   => ['RUNNING','SKIPPED','CANCELED'],
    'RUNNING' => ['SUCCESS','FAILED','RETRY','TIMEOUT','CANCELED'],
    'TIMEOUT' => ['RETRY','FAILED','CANCELED'],
    'RETRY'   => ['READY','FAILED','CANCELED'],
    'FAILED'  => ['RETRY'],
    // SUCCESS / SKIPPED / CANCELED : 종결 — 빈 배열
  ];

  public function canTransition(JobStatus $from, JobStatus $to): bool { … }

  // 주의: transition()은 자체 트랜잭션을 열지 않는다 —
  // 호출부(CommandService/Claim/Scheduler)가 소유한 트랜잭션 안에서 실행된다.
  public function transition(int $jobId, JobStatus $from, JobStatus $to,
                             string $actor, ?string $note = null): bool {
    // assert: DB::transactionLevel() > 0
    $this->assertAllowed($from, $to);
    $updated = DB::update(
      "UPDATE workflow_jobs SET status=?, updated_at=now()
       WHERE id=? AND status=?", [$to->value, $jobId, $from->value]); // CAS
    if ($updated === 0) return false;   // 동시성 충돌 — 호출부가 재조회 후 판단
    DB::insert("INSERT INTO workflow_job_histories …", [...]);        // 같은 트랜잭션
    return true;
  }
}
  • 트랜잭션 소유권: 최상위 DB::transaction()은 CommandService(관리자 조작)·JobClaimService(Worker)·Scheduler가 소유한다. StateMachine은 현재 트랜잭션 안에서 CAS UPDATE + history INSERT만 수행하며 내부에서 트랜잭션을 열지 않는다. 단독 전이가 필요한 경로는 별도 wrapper(TransitionRunner)가 트랜잭션을 연다.
  • 동일 패턴으로 ContentStateMachine, InstanceStateMachine, WorkerStateMachine, SearchIndexStateMachine 구성 — 공통 추상 클래스 AbstractStateMachine에 transition/canTransition/이력 기록을 두고 전이표만 각자 정의.
  • 모든 상태 변경은 StateMachine 서비스 경유 — Eloquent $model->update(['status'=>…]) 직접 호출 금지 (정적 분석 규칙 또는 Model observer로 차단).
  • CAS(WHERE status=?) 0행 갱신 = 동시성 충돌: 예외가 아닌 정상 분기 — 재조회 후 이미 목표 상태면 멱등 성공, 다른 상태면 포기.
  • Worker 완료 기록은 CAS에 worker_id=:me 추가(lease fencing).
  • DB trigger는 2차 방어선으로 권장(§17) — 애플리케이션 우회(수동 SQL, 마이그레이션 스크립트) 실수를 차단.

17. PostgreSQL Trigger / Constraint 제안

CHECK 제약은 상태값 목록만 검증 가능 — 전이 검증은 BEFORE UPDATE trigger + 허용 전이 테이블로 구현한다.

CREATE TABLE workflow_job_allowed_transitions (
  from_status varchar(20) NOT NULL,
  to_status   varchar(20) NOT NULL,
  PRIMARY KEY (from_status, to_status)
);
-- §5 전이표를 시드 데이터로 INSERT

CREATE OR REPLACE FUNCTION check_job_transition() RETURNS trigger AS $$
BEGIN
  IF OLD.status = NEW.status THEN RETURN NEW; END IF;  -- 상태 외 컬럼 갱신 통과
  IF NOT EXISTS (SELECT 1 FROM workflow_job_allowed_transitions
                 WHERE from_status = OLD.status AND to_status = NEW.status) THEN
    RAISE EXCEPTION 'invalid job transition: % -> % (job %)',
      OLD.status, NEW.status, OLD.id;
  END IF;
  NEW.updated_at := now();
  RETURN NEW;
END $$ LANGUAGE plpgsql;

CREATE TRIGGER trg_job_transition BEFORE UPDATE OF status ON workflow_jobs
FOR EACH ROW EXECUTE FUNCTION check_job_transition();
  • updated_at 자동 갱신은 위 트리거(또는 공용 set_updated_at 트리거)로 처리.
  • history 누락 방지 트리거(AFTER UPDATE에서 history 자동 INSERT)는 비권장 — actor/note를 트리거가 알 수 없어 이력 품질이 떨어진다. history는 애플리케이션 책임으로 유지하고, 정합성은 야간 감사 쿼리(전이 수 vs history 수 대조)로 검증.
  • 판단: 애플리케이션(StateMachine) 중심 + DB trigger는 얇은 2차 방어선. 전이표 변경 시 enum과 시드를 함께 배포(불일치 시 trigger가 먼저 막아 안전).
  • DELETED 콘텐츠 job 생성 금지: workflow_jobs BEFORE INSERT trigger에서 contents.status IN ('DELETED') 검사 → EXCEPTION.

19. 장애 시나리오별 상태 변화

시나리오상태 전이 및 후속 처리로그 기록
1. Worker가 TC 실행 중 사망heartbeat 90초 미수신 → agents=OFFLINE(System) → lock 만료·회수 → TC RUNNING→RETRY(+백오프) → 다른 Worker가 재실행history: actor=system, note=lease_expired · logs: WARN
2. Storage I/O 오류해당 job RUNNING→RETRY(일시적 분류). 동일 오류 반복 시 운영 알림 — 전역 장애 가능성logs: ERROR + storage 오류 코드
3. VERIFY 손상 파일 감지VERIFY RUNNING→FAILED(영구, 재시도 없음) → 후속 필수 job SKIPPED(실패 전파) → instance·contents FAILED → 사용자 안내history: note=PERMANENT_CORRUPT · logs: 검증 상세
4. INDEX 검색엔진 장애INDEX RUNNING→RETRY (base 30초 백오프, max 5회) → 소진 시 FAILED → contents FAILED(INDEX는 필수) + 알림. search_index_states=FAILEDlogs: 엔진 응답 코드
5. OCR 실패 (선택)OCR FAILED — PUBLISH 비차단, contents READY 진행. 대시보드 경고logs: 엔진 오류
6. PUBLISH 직전 thumbnail 누락PUBLISH 판정 실패(rendition 실재 검사) → PUBLISH FAILED(재시도 안 함, 원인=필수 산출물 누락) → 관리자 알림 → CA 수동 재실행 → PUBLISH 수동 재시도history: note=MISSING_RENDITION:THUMBNAIL
7. 관리자가 RUNNING Job 취소cancel 신호 → Worker 중단·정리 → RUNNING→CANCELED → 후속 SKIPPED → instance CANCELED(필수 경로였다면)history: actor=admin, note=사유
8. 콘텐츠 삭제 중 Job 실행 중contents→DELETED(단일 트랜잭션에서 비종결 job 일괄 CANCELED + cancel 신호) → Worker 중단 → 신규 job 생성은 INSERT 가드가 차단history: actor=system, note=content_deleted
9. Scheduler 중복 실행두 번째 인스턴스는 pg advisory lock 획득 실패 → 대기/종료. 상태 변화 없음Scheduler 프로세스 로그만

20. 운영 시 고려사항

  • 전이표 변경은 3곳 동시 배포: PHP 상수 맵, workflow_job_allowed_transitions 시드, 본 문서. 불일치 시 trigger가 먼저 차단하므로 안전하지만 배포 순서는 시드 → 코드.
  • 야간 감사 배치: history 없는 상태 변경 탐지(updated_at vs 최신 history), RUNNING인데 lock 없는 job, lock 있는데 RUNNING 아닌 job — 각각 알림.
  • 준종결 FAILED가 장기 방치되지 않도록 실패 후 N일 경과 콘텐츠 리포트를 주간 발송.
  • 상태 기계 단위 테스트: 허용 전이 전수 + 금지 전이 전수 + CAS 충돌 시나리오를 CI에 포함.
